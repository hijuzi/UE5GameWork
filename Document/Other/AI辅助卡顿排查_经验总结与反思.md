# AI 辅助下的卡顿排查复盘：发现问题、解决思路、结果、反思

一次编辑器里首次进战斗卡五六秒的排查，按复盘的四段写。排查过程里的原始日志和数据在另一份文档（`AI辅助定位游戏卡顿实战.md`），这里只写判断依据和取舍理由。

## 一、发现问题

### 1.1 现象

编辑器打开后第一次进入战斗，画面停滞五六秒。切换相机、播放进场动画都发生在停滞结束之后。第二次进入战斗正常，重启编辑器后再次复现。

### 1.2 第一判断，以及它为什么不够用

我的第一反应是 `PossessMainPlayerCombatCharacter`，理由是切相机的调用写在这句后面。代码看完没有得出任何结论，只确定了两个需要核实的位置。

当时的主要困难不在猜测方向，而在验证手段缺失：

- 日志只有流程信息，没有耗时数据
- 涉及的两处调用从代码上看都是微秒级操作，判断不出谁在等待
- 验证一次猜测要改代码、编译、试玩，最后得到的只是「感觉快了一些」

### 1.3 重新定义问题

后来把「进战斗为什么卡」拆成三个可以实测回答的问题：

1. 五六秒的时间落在哪一步，具体到函数
2. 这一步慢的性质是什么：同步加载、首次编译，还是计算量大
3. 为什么只有第一次出现

这三个问题都能用一次运行的数据回答。回头看，这次排查真正的分水岭在问题定义上，后面的工作量基本由这一步决定。

还有一条信息是随口补充的：重启编辑器之后再进战斗就不卡了。它后来决定了整个方向。只有第一次出现意味着一次性开销，那么要找的是「什么东西第一次被加载进内存」，而不是「哪段计算太慢」。

## 二、解决思路

### 2.1 总体思路

由 AI 写插桩代码，我来跑复现、读数据，每轮只回答一个问题。

之所以走这条路，是因为几个客观条件：UE 日志自带时间戳和帧号，拿到耗时不需要额外工具；插桩代码是重复劳动，写起来快，也不需要做业务设计；日志是纯文本，可以直接贴回对话，于是能形成「数据 → 假设 → 打点代码 → 新数据」的循环。

没有直接上 Profiler 有两个原因。一是当时我读不熟 Insights 的轨道和调用栈；二是判断这个问题属于「业务流程里某一步慢」，用业务语义命名的日志更快。这个判断对了一半，另一半在 4.4 里写。

### 2.2 先立规矩：没有数据不动生产代码

改业务代码需要一次编译加一次试玩，换回的是主观感受。同样的成本花在打点上，换来的是「1160 毫秒里 1159 毫秒在 `CreateCombatData`」这种可以直接判读的结论。

这条规矩这次执行住了。中间有几轮 AI 拿到数据就建议把同步调用改成异步，我没有采纳，因为当时还没确认要改的是哪一句。

### 2.3 提问方式

前几轮的效果差异主要来自问题怎么问：

| 效果差的问题 | 效果好的问题 |
| --- | --- |
| 游戏进战斗很卡，帮我看看 | 首次进战斗时 `StartBattle` 里哪一步最耗时，我想先加分段计时验证 |
| 这个函数是不是有性能问题 | 这一步耗时 1092 ms，同一段代码里的敌方角色只花 66 ms，差异可能来自哪里 |
| 怎么优化这段代码 | 这 1 秒落在哪个函数的范围里，下一步该测哪里 |

好问题的答案能被一次实测判读，差问题的答案只能是一份通用检查清单。

每次开新问题，我会提供三部分内容：现象（包含什么时候不出现）、代码位置、已知条件（日志特征、复现条件、编辑器还是打包）。

### 2.4 数据格式

贴原始日志行，不做转述。转述会丢掉时间戳和帧号，而这两项是把结论从推测变成事实的依据。一行带 `[2026.09.17-01.38.28:627][900]` 前缀的完整日志，比「角色生成似乎比较慢」有用得多。

一次运行的数据一次贴完。只贴自己认为有问题的行，会丢掉对照信息。这次的关键线索「敌方角色只用了 66 毫秒」原本夹在几行我看着无关的输出里，如果当时按主观判断删掉，还要多跑一轮。

日志加统一前缀。这次用的是 `[BattleTiming]`。它有两个作用：在 Output Log 里方便过滤，贴给 AI 时对方也能识别哪些是计时行。

每行日志带一个系统指标。只有毫秒数分不清「等加载」和「等编译」，这两类的处理方式不同。这次带的是待编译资产数，同一批数据同时回答了两个问题。

表格比段落好读。六行计时日志整理成表，重点位置不用解释就能看出来。

一次运行的数据不要拆成多条消息发送。分批发送时 AI 只能看到局部，容易给出「再测一下 HUD」这类没有依据的建议。

### 2.5 判断下一步

拿到数据之后，决定下一步测哪里，主要用下面几个方法。

先排除正常项。六个步骤里五个在毫秒级以下，可以先不管，问题范围立刻缩小到一个函数。

找同类对象对照。优先选「走同一段代码、结果差很多」的两个对象。玩家 1092 毫秒、敌方 66 毫秒，差 16 倍，结论从「哪段代码慢」变成「和这个角色类有关」。

每轮只确认一层。问的问题是「这 1 秒落在哪个函数里」，从 `StartBattle` 到 `CreateCombatData`、到 `SpawnActor`、到 `BeginPlay`、再到具体组件，一共六轮。每轮需要跑一次复现，所以要控制轮次。

自己代码里没有可疑点，就去读引擎源码。第五轮测出 `BeginPlay` 的 `Super` 段耗时 1.1 秒，而自己写在里面的代码只有一句，单独测量是 0.3 毫秒。这种情况下继续猜没有意义。查源码后发现 `AActor::BeginPlay` 会遍历所有组件逐个调用 `BeginPlay`。

用冷热对比判断性质。「第二次不卡」说明是一次性开销，处理方式只能是预热或延后，不需要去优化计算逻辑。

用引擎自带的计数器替代猜测。`FAssetCompilingManager` 可以按类型列出待编译资产数，比从代码推断「是不是在编译」可靠。

整理成表，下次可以直接照着走：

| 现象 | 说明 | 下一步 |
| --- | --- | --- |
| 帧号不动、时间戳跳几秒 | 单帧同步阻塞 | 在流程里分段计时，找出落在哪一段 |
| 帧号连续跳很多 | 多帧各自超时或后台抢占 | 查异步和分帧逻辑，配合 Insights 时间轴 |
| 同一段代码里 A 慢 B 快 | 和对象本身有关，不是流程问题 | 对照两者的类、组件、默认配置 |
| 某段耗时长、待编译数为 0 | 等同步加载 | 找那段的 `LoadSynchronous` 和硬引用 |
| 某段耗时长、待编译数在涨 | 等编译 | 按类型看是哪一类，往预热方向修 |
| 只有第一次慢 | 一次性开销 | 移到加载界面期间，或者改异步 |
| 自己代码里没有可疑点 | 开销在引擎或 BP 侧 | 读引擎源码，或抓一次 Insights |

### 2.6 实际收敛过程

| 轮次 | 加了什么 | 得到什么结论 |
| --- | --- | --- |
| 1 | `StartBattle` 六步分段计时 | 1160 ms 里 1159 ms 在 `CreateCombatData`，Possess 与相机清白 |
| 2 | 按角色分开计时 + 待编译资产统计 | 玩家 1092 ms / 敌方 66 ms；本次新排入 26 张纹理、1 个 Niagara |
| 3 | `SpawnActor` 拆成三段 | 全部落在 `SpawnActor`，授予能力集与进场 GA 都是毫秒级 |
| 4 | `BeginPlay` 拆分 | `Super` 段 1115 ms，自己写的接收者注册只有 0.3 ms |
| 5 | 读引擎源码 | `AActor::BeginPlay` 会遍历所有组件调 `BeginPlay` |
| 6 | 逐组件计时 | `SVUIExtensionManagerComponent` 占 1042 ms |

## 三、结果

### 3.1 根因

`SVUIExtensionManagerComponent::BeginPlay` 会遍历十几个 `UI.Slot.*` 标签，每个标签走 `RegisterExtensionFromTable`，里面是一次同步加载（`Plugins/GameUIFramework/Source/GameUIFramework/Private/UIExtensionSystem.cpp:396`）：

```cpp
TSubclassOf<UUserWidget> WidgetClass = Row->UserWidget.LoadSynchronous();
```

十几个 UMG 控件类连同它们的贴图、字体、特效在这一帧被拉进内存，而这段代码在本会话里是第一次执行。

### 3.2 数据

玩家角色 `SpawnActor` 1092 毫秒的分解：

| 位置 | 耗时 |
| --- | --- |
| 换装初始化（`OnConstruction`，10 个部件） | 15.5 ms |
| `PostInitializeComponents` | 0.0 ms |
| 组件 `BeginPlay` 里的 `SVUIExtensionManagerComponent` | 1042.5 ms |
| `AddGameFrameworkComponentReceiver` | 0.2 ms |
| `LinkAnimClassLayers` | 0.2 ms |

对照组是同一个流程里的敌方角色，同款组件只有 16.1 毫秒，因为它排在玩家后面，资源已经加载过。

### 3.3 现象之间的一致性

敌方同款组件 16 ms，因为资源已加载；生成玩家角色时新增 26 张纹理和 1 个 Niagara，就是这批 UMG 的依赖；重启编辑器后不卡，因为编译结果已经写进 DDC、磁盘缓存也热了；Possess、切相机、HUD 测出来都是零点几毫秒，它们只是被这一帧拖在后面，看起来像原因。

### 3.4 保留下来的东西

主流程的 `[BattleTiming]` 日志保留，之后每次进战都会输出一份耗时和待编译构成，可以当作常态埋点。计时器和待编译统计两个片段可以用在别的流程上。

### 3.5 处理方向

把 `SVUIExtensionManagerComponent` 那批 UMG 的同步加载挪到加载界面期间异步预热，或者把注册接口改成异步版本。改动还没做，先把诊断代码清理掉。

## 四、反思

### 4.1 有效的地方

第一轮先核实自己最怀疑的位置。我最怀疑 `Possess` 和切相机，AI 提议把整段 `StartBattle` 打点，而不是只测那两行。这一步大约花了半小时，收益是后续讨论都不必再考虑这两处。

每轮都跑实测。六轮里 AI 有几次判断的落点不对，怀疑过 HUD，也怀疑过换装。因为每轮都验证，猜错只是损失一轮，大约二十分钟。

补充了「什么时候不出现」。这条现象是随口报的，后来成为定方向的依据。

### 4.2 失误与返工

对照物拿得太晚。敌方角色那组数字第一轮就能拿到，我第二轮才按角色分开计时。下次应该把「同一段流程里的轻量对象」列为第一轮的必测项。

Profiler 考虑得太晚。这次问题恰好落在有 C++ 插桩点的地方。如果落在纯 BP 图、编辑器行为、着色器编译或者 DDC 命中上，日志就够不着了。范围缩到单个函数时，就应该顺手抓一份 trace 备用。

日志粒度改了三轮。先粗后细，其实可以一次规划好三层：流程级（哪个步骤）、对象级（哪个角色）、组件级（哪个组件），能少跑两轮。

为了确认结论，用了一次不该长期保留的手段。逐组件计时那段代码把引擎的组件循环搬到了自己 `BeginPlay` 的前面。我核对过 `HasActorBeginPlay()` 在两个时点的值一致，行为差异很小，但它确实改变了调用顺序。更稳妥的做法是先读源码，再找不改顺序的观测方式。

冷热态混在同一批数据里讨论。前几轮的运行环境不完全一致，有热态也有冷态，讨论时容易跑偏。下次一开始就把复现条件写清楚：DDC 是否清过、编辑器是刚启动还是已经跑了一段时间。

### 4.3 方法层面的收获

打点是假设驱动的，这一点要认。你认为哪里慢就埋哪里，问题落在没想到的模块上，打点再多也覆盖不到。这次能沿着 C++ 调用链查到组件级，和问题恰好出现在角色生成路径上有关。知道这个边界，才会在该上 Profiler 的时候上。

「看起来没有代码」的地方，往往有代码。角色 BP 里没有实现 `BeginPlay`，我一度以为这条路走不通，实际上组件的 `BeginPlay`、AnimBP 的 `BlueprintBeginPlay` 都在引擎的同一个循环里。

直觉要当假设用。我的第一判断就是错的。当成待验证的假设，错了只损失一轮；当成结论，就会被带着走很多轮。

先把卡顿分类，再谈优化。同步加载、首次编译、计算量大，这三类的处理方式不同，分类靠数据而不是读代码。

### 4.4 两条路的对照：人工 Profiler 与 AI 辅助打点

这次走的是打点这条路，但它不是通用解。两条路摆在一起，边界比较清楚。

| 维度 | 人工 Profiler（Insights / trace、stat 系列） | AI 辅助打点（日志计时） |
| --- | --- | --- |
| 前置知识 | 要会看轨道、通道、调用栈、符号解析，第一次打开基本是一屏看不懂的图 | 只要说清楚「这一步花了多少毫秒」，UE 日志自带时间戳和帧号 |
| 拿到第一个结论 | 一次抓取包含全部层级，会读的人最快 | 一次复现只回答一个问题，单轮快但要多轮 |
| 数据完整度 | 全量，调用栈、加载、线程、GPU 都在，没预料到的东西也在 | 只有埋过点的地方，没埋的地方是盲区 |
| 归因能力 | 直接给调用栈，谁触发的不用推理 | 只能给「哪一段慢」，谁触发要靠对照和推理 |
| 精度 | 微秒级，能看到顺序和重叠 | 区间级，外层包内层，测量本身还有一点开销 |
| 侵入性 | 零侵入，加个启动参数或控制台命令 | 要改代码，有遗留风险；这次还改动了引擎的组件调用顺序 |
| 复现成本 | 一次复现拿到所有层级 | 每层一次复现，这次用了六轮 |
| 二次可读性 | 需要自己看时间轴，不方便贴给别人 | 纯文本，可以直接贴给同事或 AI |
| 能否直接落到代码修改点 | 需要人再翻译成「改哪个函数」 | 结论本身就是函数名和行号，可以接着改 |
| 打包 / 真机环境 | 链路长，要带 trace 支持再把 utrace 导出来 | 放开日志级别就能用，很多时候是唯一手段 |
| 能否沉淀 | 一次性证据，抓完就结束 | 可以留成常态埋点，做回归监控 |
| 最大的风险 | 不会读，抓了等于没抓 | 没想到的地方就埋不到，容易漏 |

Profiler 的优势在完整性和归因能力。它不依赖你对代码的假设，这一点打点比不了。

打点的优势在于输出可读、结论可直接落到代码上。日志是文本，人和 AI 都能读，所以能形成循环。trace 目前还需要人工解读，AI 帮不上，这条链路是断的。

AI 改变的是打点这条路的成本结构。打点以前的问题不在原理，在成本：每加一层要手写代码、重新编译、再读一遍日志，很多人试两轮就放弃。这几件事恰好是 AI 快的部分，于是这个方法从「麻烦」变成「可用」。成本降下来之后，选路的标准也跟着变了：先看问题适合哪条路，而不是看自己会不会用 Profiler。

我现在的取舍标准：

- 问题是「某个业务流程的某一步慢」：优先打点，可以用业务语义命名，结论直接可改
- 问题落在没有 C++ 插桩点的地方（BP 图、编辑器行为、着色器编译、DDC 命中）：只能上 Profiler
- 偶发、无法稳定复现：只能上 Profiler，前提是日志已经埋好
- 涉及多线程、渲染线程、GPU：只能上 Profiler
- 需要长期监控回归：打点，固化成常态日志
- 完全不知道从哪下手：先 Profiler 看宏观，再用日志进具体流程

这次最应该改的一点，是第二轮就两条路并用。日志那时已经把范围缩到「角色生成」，这时候抓一份 trace，调用栈会直接指出 `LoadSynchronous`，后面四轮都能省掉。

### 4.5 AI 的能力边界

编辑器里的内容它看不到。BP 图、组件默认值、DataTable 配置只能人打开看。最后那句 `LoadSynchronous` 是它顺着调用链指出来的，但「这个组件挂在哪个角色上」「这批 UI 槽位是不是每个角色都要注册」需要我看过 BP 才能回答。

复现成本转移不了。每轮验证都要人跑一遍，提问策略必须围绕这个成本设计。

接口要自己核对。它给的引擎 API，我基本都让它补上文件路径和行号，或者自己翻一遍。UE 版本之间接口变动不小，报错一次的代价比核对一次高。

取舍要人定。「这个开销值不值得修」「预热放在哪个时机不影响体验」这类判断，它给不出最终答案。

### 4.6 重新做一次的话

三轮结束，不再试探粒度。

第一轮把可疑流程整段分段打点，同时挂一个系统指标，一次拿到「哪一步慢」和「是不是在编译」。第二轮按对象拆开，找到同一段代码里的轻重对照，确定问题和哪个对象绑定；同一轮把 trace 打开抓一份。第三轮直接测到最底层可见的调用单位，用引擎源码验证结论。

三轮这个数字本身不重要，重点是把这次事后才想到的几件事提前做掉：对照物、Profiler、粒度规划、复现条件记录。

```cpp
// 计时器：只测不打印，日志分类由调用点决定
struct FSVStepTimer
{
    FSVStepTimer() : StartTime(FPlatformTime::Seconds()), LastTime(StartTime) {}

    double Mark()
    {
        const double Now = FPlatformTime::Seconds();
        const double Delta = (Now - LastTime) * 1000.0;
        LastTime = Now;
        return Delta;
    }

    double Total() const { return (FPlatformTime::Seconds() - StartTime) * 1000.0; }

private:
    double StartTime;
    double LastTime;
};
```

```cpp
// 待编译资产统计：区分「等加载」和「等编译」，拼成 "224（UE-Texture=92, ...）"
inline FString SVDescribePendingCompilations()
{
    int32 TotalRemaining = 0;
    FString Breakdown;

    for (const IAssetCompilingManager* CompilingManager : FAssetCompilingManager::Get().GetRegisteredManagers())
    {
        if (!CompilingManager) { continue; }

        const int32 Remaining = CompilingManager->GetNumRemainingAssets();
        if (Remaining <= 0) { continue; }

        TotalRemaining += Remaining;
        if (!Breakdown.IsEmpty()) { Breakdown += TEXT(", "); }
        Breakdown += FString::Printf(TEXT("%s=%d"),
            *CompilingManager->GetAssetTypeName().ToString(), Remaining);
    }

    return Breakdown.IsEmpty()
        ? FString::Printf(TEXT("%d"), TotalRemaining)
        : FString::Printf(TEXT("%d（%s）"), TotalRemaining, *Breakdown);
}
```
