## GAS_MOD 标记规范（固定格式，后续所有改动必须遵循）

每处相对引擎的源码修改，必须按以下模板包裹，其中"修改前"用 `/* */` 块注释**逐字**保留引擎原版代码（含原始缩进、注释与完整逻辑）：

```cpp
//=====================================================================
// ===== [GAS_MOD_xx] START=====
// 修改前(引擎原版):
/*
<引擎原版代码，逐字一致，含原始缩进、注释和完整逻辑>
*/
// 修改后(本项目, 新建): <改动说明，可多行>
//=====================================================================
<修改后的实际生效代码>
// ===== [GAS_MOD_xx] END =====
//=====================================================================
```

**规范要点：**

1. **装饰线**：`//=====================================================================`（无空格，紧贴 `//`）。
2. **START/END 标记**：`// ===== [GAS_MOD_xx] START=====` 与 `// ===== [GAS_MOD_xx] END =====`，缩进对齐所在代码块层级。
3. **编号**：`xx` 为全局递增编号；同一逻辑改动拆分到多处时可用 `xx` 加子编号（如 `07a`/`07b`）。
4. **修改前(引擎原版)**：独立一行 `// 修改前(引擎原版):`，其下用 `/* */` 块注释**逐字**复制引擎原版代码，不得简化、不得改缩进。
5. **修改后(本项目, 新建)**：`// 修改后(本项目, 新建):` 说明改动意图；下方紧跟实际生效的新代码。
6. **新增文件**：整个文件体用 `START`/`END` 包裹（如 `GAS_MOD_09` 的 `AbilityTimerManager.h/.cpp`），`START` 下注明"新增文件"。
7. **include 语句**：新增的 `#include` 也用 START/END 包裹并标注对应编号。

## GAS_MOD_01 — GameplayCue `N*N` 重复触发修复（OnActive / WhileActive）

**文件**：`Private/GameplayEffect.cpp`
**函数**：`AddActiveGameplayEffectGrantedTagsAndModifiers`（GE 首次应用、预测路径）
**问题本质**：外层 `for (Cue : Def->GameplayCues)` 已遍历每个 Cue，引擎原版却在循环体内调用 `InvokeGameplayCueEvent(Spec, ...)`；该函数内部会**再次遍历全部 Cue**，于是 N 个 Cue → N×N 次触发。

### 修改前（引擎原版）
```cpp
// 外层已 for 遍历到某个 Cue
if (bInvokePredictedEffects)
{
    Owner->InvokeGameplayCueEvent(Effect.Spec, EGameplayCueEvent::OnActive);
    Owner->InvokeGameplayCueEvent(Effect.Spec, EGameplayCueEvent::WhileActive);
}
```

### 修改后（本项目，`GAS_MOD_01` 包裹，当前代码 4744 ~ 4785）
```cpp
//=====================================================================
// ===== [GAS_MOD_01] START=====
// 修改前(引擎原版):
/*
Owner->InvokeGameplayCueEvent(Effect.Spec, EGameplayCueEvent::OnActive);
Owner->InvokeGameplayCueEvent(Effect.Spec, EGameplayCueEvent::WhileActive);
// 缺陷: InvokeGameplayCueEvent(Spec) 内部会再次遍历 Def->GameplayCues 全部 Cue,
//       而外层 for 已遍历每个 Cue => 外层 x 内层 = N*N 次触发。
*/
// 修改后(本项目, 新建): 仅对当前 Cue 内联构造参数并直接 HandleGameplayCues, 降为 O(N),
// 同时补全 RawMagnitude / NormalizedMagnitude / bGameplayEffectActive。
//=====================================================================
FGameplayCueParameters CueParameters(Effect.Spec);
if (Cue.MagnitudeAttribute.IsValid())
{
    if (const FGameplayEffectModifiedAttribute* ModifiedAttribute = Effect.Spec.GetModifiedAttribute(Cue.MagnitudeAttribute))
    {
        CueParameters.RawMagnitude = ModifiedAttribute->TotalMagnitude;
    }
    else
    {
        CueParameters.RawMagnitude = 0.0f;
    }
}
else
{
    CueParameters.RawMagnitude = 0.0f;
}
{
    const float Level = Effect.Spec.GetLevel();
    const float Range = Cue.MaxLevel - Cue.MinLevel;
    CueParameters.NormalizedMagnitude = (Range > KINDA_SMALL_NUMBER) ? ((Level - Cue.MinLevel) / Range) : 1.f;
}

FGameplayEffectQuery EffectQuery;
EffectQuery.EffectDefinition = Effect.Spec.Def->GetClass();
CueParameters.bGameplayEffectActive = Effect.Spec.Def->DurationPolicy == EGameplayEffectDurationType::Instant || GetActiveEffectCount(EffectQuery) > 0;

if (AActor* ActorAvatar = Owner->AbilityActorInfo.IsValid() ? Owner->AbilityActorInfo->AvatarActor.Get() : nullptr)
{
    UGameplayCueManager* CueManager = UAbilitySystemGlobals::Get().GetGameplayCueManager();
    CueManager->HandleGameplayCues(ActorAvatar, Cue.GameplayCueTags, EGameplayCueEvent::OnActive, CueParameters);
    CueManager->HandleGameplayCues(ActorAvatar, Cue.GameplayCueTags, EGameplayCueEvent::WhileActive, CueParameters);
}
// ===== [GAS_MOD_01] END =====
//=====================================================================
```

**要点**：单 Cue 触发从 O(N²) 降为 O(N)；同时补全了 `RawMagnitude`、`NormalizedMagnitude`、`bGameplayEffectActive` 的赋值，语义与引擎 `InvokeGameplayCueEvent(Spec)` 内部逻辑等价但只作用于当前 Cue。

## GAS_MOD_03 — StackOverflow 边界判定修复

**文件**：`Private/GameplayEffect.cpp`
**函数**：`FActiveGameplayEffectsContainer::HandleActiveGameplayEffectStackOverflow`
**问题本质**：引擎用 `==` 判"是否已达堆叠上限"，存在两个边界缺陷。

### 修改前（引擎原版）
```cpp
// allow refreshing duration and context ...
using namespace UE::GameplayEffect;
const bool bAtStackLimit = OldSpec.GetStackCount() == StackedGE->StackLimitCount;
```

### 修改后（本项目，`GAS_MOD_03` 包裹，当前代码 3709 ~ 3720）
```cpp
//=====================================================================
// ===== [GAS_MOD_03] START=====
// 修改前(引擎原版):
/*
const bool bAtStackLimit = OldSpec.GetStackCount() == StackedGE->StackLimitCount;
// 缺陷:
//   1) GE 未配置堆叠上限(StackLimitCount==0)且当前层数为 0 时, 会被误判为已到上限;
//   2) 用 == 而非 >=, 在层数被 FMath::Min() 截断/归并的路径下不够健壮。
*/
// 修改后(本项目, 新建): 先用 bHasStackLimit 兜底(未设上限则永不判到顶), 再以 >= 判定是否到达上限。
//=====================================================================
const bool bHasStackLimit = StackedGE->StackLimitCount > 0;
const bool bAtStackLimit = bHasStackLimit && OldSpec.GetStackCount() >= StackedGE->StackLimitCount;
// ===== [GAS_MOD_03] END =====
//=====================================================================
```

**修复点说明**：
1. **未设上限误判**：当 GE 未配置堆叠上限（`StackLimitCount == 0`）且当前层数为 `0`（如首次应用尚未叠加）时，引擎原版 `0 == 0` 会误判 `bAtStackLimit == true`，从而错误进入"刷新/Overflow 应用"分支。`bHasStackLimit` 兜底后，未设上限则永不判到顶。
2. **`==` 改 `>=`**：层数可能经 `FMath::Min()` 截断/归并后恰等于上限，用 `>=` 判定更健壮。
> 注：`bAtStackLimit` 之后仅影响 `bRefreshToLimit` 的计算与函数返回值；该函数内 `OverflowEffects` 的应用逻辑与引擎保持一致，未作改动。

## GAS_MOD_04 — PRAGMA 屏蔽 UE5.8 弃用告警（GetInstancingPolicy）

**文件**：`Private/AbilitySystemBlueprintLibrary.cpp`
**函数**：`UAbilitySystemBlueprintLibrary::HasAnyAbilitiesByPredicate`
**问题本质**：UE 5.8 将 `GetInstancingPolicy()` 标记为废弃（Deprecated），直接调用会产生弃用告警；项目仍需读取实例化策略做兼容判定。

### 修改前（引擎原版）
```cpp
if (!bOnlyRunPredicateOnAbilityCDOs && Spec.Ability->GetInstancingPolicy() != EGameplayAbilityInstancingPolicy::NonInstanced)
{
    AbilitiesToCheck.Append(Spec.GetAbilityInstances());
}
else
{
    AbilitiesToCheck.Add(Spec.Ability);
}
```

### 修改后（本项目，`GAS_MOD_04` 包裹，当前代码 1562 ~ 1581）
```cpp
//=====================================================================
// ===== [GAS_MOD_04] START=====
// 修改前(引擎原版):
/*
if (!bOnlyRunPredicateOnAbilityCDOs && Spec.Ability->GetInstancingPolicy() != EGameplayAbilityInstancingPolicy::NonInstanced)
{
    AbilitiesToCheck.Append(Spec.GetAbilityInstances());
}
else
{
    AbilitiesToCheck.Add(Spec.Ability);
}
// 问题: UE5.8 已将 GetInstancingPolicy() 标记为废弃(Deprecated), 直接调用会产生弃用告警。
*/
// 修改后(本项目, 新建): 用 PRAGMA_DISABLE_DEPRECATION_WARNINGS / PRAGMA_ENABLE_DEPRECATION_WARNINGS
// 包裹该调用, 屏蔽 UE5.8 的弃用告警, 保持向后兼容。
//=====================================================================
PRAGMA_DISABLE_DEPRECATION_WARNINGS
if (!bOnlyRunPredicateOnAbilityCDOs && Spec.Ability->GetInstancingPolicy() != EGameplayAbilityInstancingPolicy::NonInstanced)
{
    AbilitiesToCheck.Append(Spec.GetAbilityInstances());
}
else
{
    AbilitiesToCheck.Add(Spec.Ability);
}
PRAGMA_ENABLE_DEPRECATION_WARNINGS
// ===== [GAS_MOD_04] END =====
//=====================================================================
```

**要点**：改动不改变任何运行逻辑，仅通过 `PRAGMA_DISABLE/ENABLE_DEPRECATION_WARNINGS` 临时屏蔽 `GetInstancingPolicy()` 的 UE5.8 弃用告警；`if/else` 分支（取 Ability 实例 或 CDO）逻辑与引擎完全一致。

> 该改造与 `GAS_MOD_09` 同属 `AbilityTimerManager.h/.cpp`，共用文件级标记 `GAS_MOD_09`。本节给出改动前/后对照。

**文件**：`Public/AbilityTimerManager.h` + `Private/AbilityTimerManager.cpp`

**修改前（`GAS_MOD_09` 初版）**：

```cpp
struct FAbilityTimerContainer
{
    int32 Turn = 0;                     // 单一匿名刻度
    TArray<FTimerHandle> TimerHandles;
};
```

**修改后（本项目）**：

```cpp
/** 某条时间轴（某个"时机"）的运行状态 */
struct FAbilityTimerAxis
{
    int32 Counter = 0;                    // 该时机已推进的刻度
    TArray<FTimerHandle> TimerHandles;    // 挂在该时机上的 Timer
};

/** 每个 ASC 的计时容器：按时机 Tag 分组，各轴独立推进 */
struct FAbilityTimerContainer
{
    TMap<FGameplayTag, FAbilityTimerAxis> Axes;
};

void TickTimeline(ASC, FGameplayTag InTiming, int32 Delta = 1);   // 取代 TickTurn
void SetAbilityTimer(ASC, FGameplayTag InTiming, FTimerHandle&, Delegate, Rate, bLoop, FirstDelay);
float GetAbilityTimerRemaining(ASC, FGameplayTag InTiming, FTimerHandle&);
int32 GetTimelineCounter(ASC, FGameplayTag InTiming) const;       // 取代 GetAbilityCurrentTurn
void RemoveAbilityTimer(ASC, FGameplayTag InTiming, FTimerHandle&);
```

**`TickTimeline` 要点**：

- `InTiming.MatchesTag(AxisTag)` 命中"被匹配的轴（含父级）"：`InTiming = TimeAxis.Action.Attack` 会同时推进 `Action.Attack` 轴与父级 `Action` 轴；
- 推进前**快照命中的轴 Tag 与句柄数组**，避免回调（如 Duration 到期移除 GE）修改容器导致迭代器失效；
- 到期执行前**快照 `bLoop` / `Rate`**，避免回调清 Timer 后访问失效的 `FTimerData`；
- 循环 Timer 执行后顺延 `ExpireTime = Counter + Rate`；一次性 Timer 执行后移除并 `ClearTimer`。

## GAS_MOD_13 — 插件形式编译适配（`*.Build.cs` + 委托执行）

> 背景：本项目把引擎插件 `GameplayAbilities` **拷贝到项目内以"项目插件"形式编译**，而引擎里那份是预编译二进制，
> 因此引擎源码中两处"依赖引擎内部模块可见性 / 内部符号导出"的写法，在插件形式下无法编译或链接。
> (a) 通过 Build.cs 补 include 路径解决（C++ 源码保持与引擎原版逐字一致）；(b) 与 include 无关，是本次多时间轴改造引入的链接问题。

### (a) `Internal` 目录下的头文件不可见

**文件**：`Source/GameplayAbilities/GameplayAbilities.Build.cs`、`Source/GameplayAbilitiesEditor/GameplayAbilitiesEditor.Build.cs`

**修改前（引擎原版）**：两个 Build.cs 中均无相关配置。

**问题本质**：引擎源码中 `AbilitySystemComponent.cpp` include 了 `UObject/UObjectMigrationContext.h`（位于 `CoreUObject/Internal/`），
`SGameplayCueEditor.cpp` include 了 `SAddNewGameplayTagWidget.h`（位于 `GameplayTagsEditor/Internal/`）。
UBT 规定模块的 `Internal` 目录只对"其它**引擎内部**模块"暴露（见 `ModuleRules.InternalIncludePaths` 注释）；
引擎自带的 `GameplayAbilities` 属于内部模块（且以预编译二进制分发），而拷贝到项目内以"项目插件"形式编译时该目录不在 include 路径中，
产生 `fatal error C1083: 无法打开包括文件`。

**修改后（本项目）**：

```csharp
// GameplayAbilities.Build.cs（运行时模块）：把依赖模块 CoreUObject 的 Internal 目录加入私有 include 路径
PrivateIncludePaths.Add(System.IO.Path.Combine(GetModuleDirectory("CoreUObject"), "Internal"));

// GameplayAbilitiesEditor.Build.cs（编辑器模块）：把 GameplayTagsEditor 的 Internal 目录加入私有 include 路径
PrivateIncludePaths.Add(System.IO.Path.Combine(GetModuleDirectory("GameplayTagsEditor"), "Internal"));
```

> 用 `ModuleRules.GetModuleDirectory("<依赖模块名>")` 取该模块根目录，避免硬编码引擎安装路径；
> `System.IO.Path` 用全限定名，因此无需额外的 `using System.IO;`。
> 之所以选择改 Build.cs 而不动 C++ 的 include，是为了让插件源码与引擎原版**逐字一致**，便于后续引擎升级时回刷合并。

### (b) `FTimerUnifiedDelegate::Execute()` 跨 DLL 未导出

**文件**：`Private/AbilityTimerManager.cpp`（`FAbilityTimerManager::TickTimeline`）

**修改前（本项目早期写法）**：

```cpp
Data->TimerDelegate.Execute();
```

**问题本质**：`FTimerUnifiedDelegate::Execute()` 在 `TimerManager.h` 中声明为 `void Execute() const;`（**无 `ENGINE_API`**），
引擎内部同 DLL 可直接调用，插件跨 DLL 调用产生 `error LNK2019: 无法解析的外部符号`。

**修改后（本项目）**：

```cpp
// 取内部 VariantDelegate 中的 FTimerDelegate 直接执行（TryGet / TDelegate::Execute 均为 inline）
if (FTimerDelegate* NativeDelegate = Data->TimerDelegate.VariantDelegate.TryGet<FTimerDelegate>())
{
    NativeDelegate->Execute();
}
```

**结果**：`GameWorkEditor Win64 Development` 编译**通过**（`Result: Succeeded`）。
